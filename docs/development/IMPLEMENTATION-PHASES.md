# Implementation phases

Order of work for the Incus-first platform ([ADR 0001](../adr/0001-incus-first.md), [architecture](../architecture/PLATFORM-ARCHITECTURE.md)). One phase at a time; a phase is done only when its acceptance checks have evidence. Every result is labelled **MOCK VERIFIED**, **CONTRACT VERIFIED** or **REAL INCUS TESTED**; anything else is NOT TESTED.

Standing rules for every phase:
- Keep Studio working; run the full Studio checks (`npm run typecheck && npm run lint && npm test && npm run build && npm run test:e2e`) before and after.
- Rust: `cargo fmt --check`, `cargo clippy --workspace -- -D warnings`, `cargo test --workspace`.
- No infrastructure mutation except on an explicitly designated, disposable test cluster, after a dry run.
- No fabricated telemetry, deployments or HA claims; no TLS verification bypass; no secrets in the repository.
- Update docs and record significant decisions as ADRs.

## 04 — Cluster management and appliance deployment

Read-only host preflight (kernel ≥ 6.12, Incus version, clock drift, member latency ≤ 10 ms, DNS, TLS, pools, networks, project restrictions, capacity). Surface Incus bootstrap/join with short-lived tokens and operator approval. Instance create/start/stop/delete with async operation tracking for the three runtimes, image architecture and digest checks, restricted projects by default. Catalog runtime fields (see `appliance-catalog`). Local-development storage profile; cross-member networking only claimed after it is tested.
**Accept:** on the test cluster: members shown, project verified, disposable LXC and OCI instances created/started/stopped/deleted with operation ids, nothing unrelated touched, no secrets leaked.

**Status (slice 1 done, CONTRACT VERIFIED — not yet REAL INCUS TESTED):** instance create/start/stop/delete for system containers, OCI containers and VMs. The API (`POST /api/v1/instances`, `POST …/{project}/{name}/state`, `DELETE …/{project}/{name}`, `GET /api/v1/jobs/{id}`) checks the `deploy` permission, validates names, allows only the projects in `APELORA_DEPLOY_PROJECTS` (default `apelora`), honours `Idempotency-Key`, audits the request and queues a job. The worker converges level-triggered: it re-reads the instance before every call, records the Incus operation id before waiting on it (fenced), waits on an earlier attempt's operation after a crash, stops before deleting, and rejects without retrying anything lacking Apelora's ownership marker (`user.apelora.managed=true`). Tested with spec-shaped fixtures for the Incus calls and real PostgreSQL for the queue. In mock mode the control plane and the worker each hold their own in-memory mock, so mock deployments appear only in the worker's log. Slice 2 done: read-only preflight (`GET /api/v1/preflight`): Incus ≥ 7.0, kernel ≥ 6.12, required API extensions (`instance_create_start`, `operation_wait`; `instance_oci` for OCI), member status, deploy projects exist and are restricted, a ready storage pool and managed network. Clock drift and member latency are reported as not checked: the Incus API cannot measure them. Slice 3 done: image pinning and architecture checks. A simplestreams image is pinned by its Incus fingerprint (sent as `source.fingerprint`, which Incus prefers to the alias), an OCI image by a digest in the alias (`repository@sha256:…`); `architectures` lists what the image supports. Before creating, the worker refuses a spec no cluster member can run (retries while suitable members are offline); afterwards it compares Incus's `volatile.base_image` and architecture with the spec and refuses, without changing anything, an existing instance that does not match.

**REAL INCUS TESTED (2026-10-20, Incus 7.0.1, one-member cluster on Debian 13 arm64, [test cluster](TEST-CLUSTER.md)):** automated in `services/deployment-worker/tests/real_incus.rs` — system container, OCI container (by tag and by digest) and virtual machine created, started, stopped, started and deleted through the job queue; re-creates and repeated deletes converge without Incus calls; a new instance created from a fingerprint pin is built from exactly that image; an existing instance on the wrong architecture is refused; a spec no member can run is refused before anything is created; an instance Apelora did not create is refused (stop and delete) and left running. Manual run the same day: members, restricted project and passing preflight through the API; the lifecycle through the HTTP API and a separately running worker with a token (`Idempotency-Key` replay, `default` project refused, every request audited, operation ids in the worker log), the Fabric Console showing the real instances in a browser, and no secrets in logs or audit. Only unit-tested: retrying while suitable members are offline, and refusing aliases in mixed-architecture clusters (one member, one architecture). The real cluster found two defects the contract tests had not: an empty profile list removed the `default` profile (fixed: omitted when empty) and an X.509 v1 client certificate (fixed in the setup script; the adapter now names the problem).

Slice 4 done: catalog runtime fields. `ApplianceClass.runtime` (system container, OCI container or VM) with one image or an image chosen by an enum setting that must cover every option; OCI images only by digest; `instanceRequestFor` maps a placed appliance to the API's `InstanceSpec` (type-checked against the generated client). NGINX (stable 1.30.6 and mainline 1.31.7, by digest) and Debian (12, 13) are deployable; the other 81 classes stay design-only until their images have run on the test cluster. REAL INCUS TESTED: every catalog runtime request created, running and deleted on the test cluster (`catalog_runtimes_run`). The local-development storage profile is the test cluster's: a btrfs pool on a loop file and a project `default` profile with root disk and NIC (`scripts/test-cluster/up.sh`).

Slice 5: cluster membership ([ADR 0003](../adr/0003-incus-identities-and-cluster-join.md)). A separate, optional, unrestricted admin identity loaded only by the control plane; a fabric administrator approves a new member by asking for its single-use join token (`POST /api/v1/cluster/join-tokens`), which is shown once and never stored, logged or audited; pending tokens are listed without secrets and can be revoked; tokens living longer than an hour get a warning. Bootstrap of the first member stays on its host (`incus admin init`). REAL INCUS TESTED (2026-10-20): a second member was approved through `POST /api/v1/cluster/join-tokens` and joined with that token (piped to `scripts/test-cluster/add-member.sh`, never on a command line); the API then showed two online members and no pending token, preflight reported "2 online", and `join_tokens_need_the_admin_identity_and_can_be_revoked` (issue, list without secret, revoke; refused for the deploy identity) and the whole real suite passed on the two-member cluster. The join first failed because the VMs' NAT network isolates VMs from each other; members now talk over a separate network.

Remaining: a run on 7.0.2 itself.

## 07 — Network fabric, service discovery, publishing

Network intent compiler (graph → intents → diff → apply), stable service names mapped to healthy replicas, deny-by-default ACLs per project, MVP VLAN profile then optional OVN profile (networks, ACLs, DNS zones, forwards, load balancers). Publishing: shared HTTPS ingress (default), private, dedicated address, internal name; domains and TLS certificates; DNS integration.
**Accept:** compiled-intent snapshot tests; isolation tests; on the test cluster, a consumer reaches a service by name across members and keeps working when a replica is replaced.

**Status (slice 1 done, compiler only — nothing is enforced on the cluster yet):** `compileNetwork(assembly, application)` in `@apelora/assembly-model` turns cables and link tags into allow rules (consumer output → provider input, protocol and well-known port, provider's stable name `<appliance>.<application>.internal`), services with their endpoints, and NIC segments (tagged, cabled, or `default`); deterministic (sorted, order-independent), deny by default (`allows`), generic TCP terminals flagged. Snapshot, determinism, isolation and tag tests. The Studio's deploy review lists the rules and says they are not enforced yet. OVN on the test cluster (`scripts/test-cluster/ovn.sh`): REAL INCUS TESTED that instances on different members reach each other by name over an OVN network, and that ACLs enforce deny by default with per-port allow rules — but only with IP/address-set rules: ACL subject selectors failed across members (details in TEST-CLUSTER.md). Enforcement design therefore: per application one OVN network; per appliance an ACL and an address set holding its instances' addresses (kept current by the worker); for each intent, the consumer's egress and the provider's ingress allow the declared port between the two address sets. Slice 2 done: enforcement. With `APELORA_NETWORK_UPLINK` set, a deployment that carries the design's connections attaches every new instance's NIC to the application's OVN network with its own ACL (unmatched traffic rejected both ways), and a `network.sync` job ensures the network, one ACL and one address set per appliance, fills the sets with the instances' addresses (retrying while instances start) and writes matching egress/ingress rules on both sides; Apelora never adopts objects without its marker. Without an uplink the plan says connections are not enforced. The Studio sends the connections between deployed appliances and says whether they are enforced. REAL INCUS TESTED (manual run, two members): client on member 1 reached `web-01` on member 2 by name on port 80; port 22, an unconnected appliance on the same member, and the reverse direction were all blocked. Network objects carry `user.apelora.application`, so cleanup never touches another application's objects (a name prefix never decides ownership); `network.sync` deletes the ACLs, then the address sets, of appliances that left the design, and the network with the last appliance — REAL INCUS TESTED (deploy, then remove everything: instances, ACLs, address sets and network gone). Slice 3 done: publishing. A gateway in the design stands for the outside world; the Studio sends what it connects to (deployed appliance, transport, well-known port) as `published`; the API validates it, warns when publishing needs enforced connections and a service range, and records it; `network.sync` gives each published appliance a service address (even a single instance) and an ingress rule open to any source on that port only. The network outside must route the service address to the application network's router. REAL INCUS TESTED (three members): with that route, an outside client reached the published port, an unpublished one stayed blocked. Slice 4 done: internet access. Each appliance has an *Internet access* setting in the Studio (none — the default —, web and DNS, any port), sent with the deployment; `network.sync` adds egress rules to `@external` only (never an any-destination rule, which would open the other appliances); the plan warns when it cannot be enforced. REAL INCUS TESTED (three members): a client with web access fetched from a public mirror, port 22 outside stayed blocked, its connection inside still worked. Slice 5 done: service discovery ([ADR 0004](../adr/0004-service-discovery.md)). Service addresses are allocated at deployment, before instances exist; every consumer is created with `APELORA_SERVICE_<PROVIDER>` per connection — the provider's service address, or its instance name (resolved by OVN's DNS) when it has none; recreated and substituted instances get the same values; a design cannot set these variables itself; the Studio's deploy review shows them. REAL INCUS TESTED (three members): inside a client, `$APELORA_SERVICE_WEB_01` reached the replicated web service and `$APELORA_SERVICE_DB_01` resolved to the database. DNS names remain possible later as an optional resolver appliance.

## 08 — Coordination, HA and mobility

PostgreSQL leases/generations; separate member/instance/service/ingress/storage health with hysteresis, grace periods, cooldowns; stateless replica policy with anti-affinity via verified Incus mechanisms; replace-then-retire relocation; policy-aware evacuation with dry run and per-item reasons (M1), replica-aware recovery (M2), advanced HA with tested fencing and shared storage (M3). Stateful single writers blocked on ambiguity. One recovery authority per workload; Incus healing stays off unless enabled deliberately.
**Status (slice 1 done: replicas, anti-affinity, restoration):** classes declare `runtime.availability` (`stateless`, `singleton` — the default — or `stateful`; NGINX is stateless); a stateless appliance takes 1–9 replicas (Studio Properties → Availability), named `<application>-<appliance>` then `-r2`…, labelled `user.apelora.replica`; the API refuses replicas for anything not stateless and the plan names every single point of failure. Each deployment's desired state is recorded (`application_deployments`); the worker's replica supervisor (every `APELORA_SUPERVISE_SECS`, default 30) queues an ordinary create job for a lost stateless replica — never while one is in flight, with a five-minute back-off after a failure — audits `application.replica.recreate`, and re-syncs the application's address sets; singleton and stateful instances are reported, never recreated. Anti-affinity uses Incus's placement scriptlet (`infra/incus/placement.star`, installed by the Incus operator; `scripts/test-cluster/placement.sh` on the lab): fewest replicas of the same appliance first. REAL INCUS TESTED (two members, 2026-10-20): two replicas placed on different members although member 2 carried more load (without the scriptlet both landed on member 1); a deleted replica was recreated by the supervisor on the member without its sibling. Slice 2 done: service addresses and restarts. With `APELORA_SERVICE_ADDRESSES` (a routed range of the uplink), every stateless appliance others connect to gets an OVN load balancer over its replicas with health checks (address allocated in PostgreSQL, released with the appliance; listed by the status API and in the Studio overlay, which now shows every replica and a degraded state). The supervisor also restarts a stateless replica that stopped behind Apelora's back (`application.replica.restart`) but respects a stop made through Apelora. REAL INCUS TESTED end to end through the control plane and worker (two members, 2026-10-20): requests to the service address alternated between replicas on different members; after one replica was force-stopped, all requests went to the other within four seconds; the supervisor restarted it within a pass and it rejoined; after it was deleted, the supervisor recreated it at the same address and the load balancer rebound to the new instance; removing the application deleted instances, network, ACLs, address sets and load balancer. Slice 3 done: evacuation with a dry run. `GET /api/v1/cluster/members/{member}/evacuation` explains, per instance on the member, what Incus will do (from its effective `cluster.evacuate` mode) and what that means for its application (replicas elsewhere keep the service up; singletons and stateful appliances are down while they move or until restore), names what blocks it (no other online member, no member of the instance's architecture, member not Online) and warns when replicas will share the last member. `POST …/evacuate` and `…/restore` need `manage-infrastructure`, the admin identity and the member's name typed again; evacuating re-runs the dry run and refuses while anything blocks it; both are audited. The Fabric Console's Membership view lists members with Evacuate…/Restore… (dry run table, type-to-confirm). The supervisor leaves instances on a member that is not Online to Incus. REAL INCUS TESTED (two members, 2026-10-20, through the control plane): the dry run for member 1 predicted both instances moving and the client being down; evacuation took about ten seconds, the instances kept their addresses on the OVN network, the service address answered from both replicas throughout, the supervisor did not interfere; restore moved them back; both actions audited. Verified in a real browser against the cluster. Slice 4 done: recovery from a failed member (replace, then retire). Replica slots are matched by labels, so a slot may be filled by a substitute `<replica>-s<n>`; an instance whose member is unreachable (listed with no configuration) still counts in its slot by name. A member that stays Offline longer than `APELORA_RECOVER_AFTER_SECS` (default 120; hysteresis kept by the supervisor) has its stateless replicas substituted on another member; when it returns, the slot's extra instance is retired, keeping the one that puts replicas back on different members; singletons and stateful appliances are only reported. Address sets and load balancer backends follow the slot's reachable instances; a failed network sync is retried after a minute; a load balancer whose health check went missing is repaired. REAL INCUS TESTED (two members, member VM force-stopped three times): the substitute appeared 31 s after the recovery delay began, the load balancer swapped the dead backend for it and requests stopped failing; on return the supervisor retired the substitute and kept the original on the returned member; a lost health check (state `unknown`) was reinstated by the next sync. Findings in TEST-CLUSTER.md (instances with `config: null`, health checks blind to a dead member, a restricted identity losing its project after a project was recreated). Slice 5 done: health with hysteresis. The worker decides each running service replica's health from the OVN load balancer's per-backend port check (`apelora_domain::health`: unhealthy after failing 20 s, healthy after passing 20 s, `unknown` neither confirms nor clears; `APELORA_HEALTH_FAIL_AFTER_SECS`), records it (`instance_health`, migration 0009) and restarts a stateless replica unhealthy for 60 s (`APELORA_HEALTH_RESTART_AFTER_SECS`) with a one-shot `instance.restart` job — at most one replica per appliance per pass, least recently restarted first, the same one not again within five minutes — audited `application.replica.restart-unhealthy`; singleton and stateful appliances are only reported. The status API reports health for running instances; the Studio counts unhealthy replicas as not serving (*Degraded*, *Unhealthy*). Runbook: `docs/runbooks/replica-unhealthy.md`. REAL INCUS TESTED (four members, `demo.sh`, 2026-10-20): with one NGINX replica's port closed while it kept running, it was reported unhealthy after 36 s, the service answered from the other replica only, the supervisor restarted it once after 66 s and not again while it stayed broken, and it was healthy 40 s after the port reopened. The check is a TCP connection: an application that hangs behind an open port is not detected. Worker restart and duplicate requests REAL INCUS TESTED (`scripts/test-cluster/drill-worker-restart.sh`: worker killed mid-create, the next one waited on its Incus operation after the lease expired, exactly the instances asked for; a repeated request queued nothing new). Remaining: names for service addresses, partition tests, a preflight check that the deploy identity can use its projects, relocation for rebalancing.

**Accept (disposable lab):** stop one stateless replica → ingress reroutes and the desired count is restored without duplicates; ambiguous database/host failure → alert and block, not a second writer; worker restart and duplicate requests handled; all actions audited.
